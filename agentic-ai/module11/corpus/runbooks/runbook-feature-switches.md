# Runtime feature switches during an incident

A runtime feature switch turns a code path off without a deployment, which makes it the fastest reversible lever during an incident. Before proposing a switch, confirm from the deployment history that the failing behavior arrived with a release that also introduced the switch. Check that turning the switch off leaves data written by the new code readable, because some releases add columns or fields that downstream reports start to depend on. A switch change is still a production change: it needs the owning team's approval and an entry in the incident record. State which switch you propose to change, what the expected effect on error rate and latency is, and how the team can confirm the effect from metrics afterwards. If the switch does not exist or its state cannot be read, fall back to the rollback runbook for the service. The investigator never flips a switch directly; it writes the proposal, labels it as not executed, and leaves the decision with the human owner.
