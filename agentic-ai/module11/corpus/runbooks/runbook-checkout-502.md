# Checkout service returns 502 after a deploy

Use this runbook when checkout-service starts returning HTTP 502 responses shortly after a deployment. First, find the most recent checkout-service deployment and compare the time it finished with the time the 502 rate rose. A rise within a few minutes of a rollout points at the change, not at a downstream outage. Next, compare the 5xx rate, p95 latency and request volume before and after the deployment; unchanged request volume with a sharp 5xx rise suggests the new version cannot serve normal load. Then read the checkout-service error logs for upstream messages such as connection pool exhausted, upstream timeout or peer closed connection, and quote the exact line in the incident record. If the deployment changed connection pool size, keep-alive reuse or client timeouts, treat that change as the probable cause and also follow the connection pool runbook. The recommended remediation is a rollback to the previous checkout-service version or a reviewed configuration change that restores the old pool size. Never roll back on your own: propose the rollback, state that it is not executed, and wait for the checkout release owner to approve it. Record the deployment ID, the quoted log line and the proposal in the incident note before you close the investigation.
