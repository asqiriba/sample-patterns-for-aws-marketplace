# Upstream connection pool exhaustion

Connection pool exhaustion happens when a service holds fewer upstream connections than its normal concurrency needs. The symptom is a log line that reports the pool as fully in use, for example eight of eight connections, followed by queued requests that time out and surface as 502 or 504 responses. Check the pool metric: a value pinned at the configured maximum while request volume is unchanged confirms exhaustion rather than a traffic spike. Compare the configured pool size in the current and previous release, because a reduced maximum is the most common cause after a deploy. Keep-alive reuse can make the problem worse when the upstream closes idle connections first, which shows up as reused after peer close warnings. Safe remediations are restoring the previous pool size through a reviewed configuration change, or rolling back the release that reduced it. Raising the pool far above the previous value is not a fix during an incident, because it can overload the upstream service. Any change to production configuration needs approval from the owning team before it is applied, and the investigator only proposes it.
