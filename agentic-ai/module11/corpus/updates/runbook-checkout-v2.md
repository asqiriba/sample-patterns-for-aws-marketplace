# Checkout service returns 502 after a deploy

Use this runbook when checkout-service starts returning HTTP 502 responses shortly after a deployment. First, find the most recent checkout-service deployment and compare the time it finished with the time the 502 rate rose. A rise within a few minutes of a rollout points at the change, not at a downstream outage. Next, compare the 5xx rate, p95 latency and request volume before and after the deployment; unchanged request volume with a sharp 5xx rise suggests the new version cannot serve normal load. Then read the checkout-service error logs for upstream messages such as connection pool exhausted, upstream timeout or peer closed connection, and quote the exact line in the incident record. If the deployment changed connection pool size, keep-alive reuse or client timeouts, treat that change as the probable cause and also follow the connection pool runbook. Before proposing a rollback, check the checkout-service feature switches: since the v2 release process, pool and timeout changes ship behind the checkout-pool-tuning switch, and turning that switch off restores the previous pool settings without a redeploy. The recommended remediation is to propose switching checkout-pool-tuning off; a rollback to the previous checkout-service version is the fallback when the change did not ship behind a switch. Never change a switch or roll back on your own: propose the action, state that it is not executed, and wait for the checkout release owner to approve it. Record the deployment ID, the quoted log line and the proposal in the incident note before you close the investigation.
